Classic & Balanced Workspaces

When both interfaces are enabled, use the Classic / Balanced links in the header to open the other layout in a separate tab. Your current tab and its editable setup remain where they are. The Classic interface is preserved at /classic; the new Balanced workspace is at /balanced.

Both layouts use the same test controls, request generator, runner, setup files, tooltips, and analysis views. Import the same exported setup into each tab to compare them. Each tab has its own form; only one load-test run can be active on the shared runner. Switching focus refreshes the displayed run status.

Balanced Layout

The compact APIs sidebar shows method, name, path, and percentage where applicable. Use the + beside APIs to add a request. Selecting a row opens its existing request settings. The filter narrows the visible list only: it does not exclude any API from a test.

Use Request, Field rules, and Payload preview to focus the middle pane. Headers, bearer tokens, expected status codes, body uploads, and scenario datasets remain in the Request view. The existing external-link icons still open larger read-only analysis tabs.

Traffic mode contains every existing option: Normal, Burst, Multi-API Burst, Weighted, and Coordinated. Their execution behavior is unchanged. Percentage allocation, shared records, single/repeated bursts, data strategy, Unique rules, and recording controls work as described elsewhere in this guide.

Resize the Panes

Drag the vertical divider beside the API list to give more space to the payload. Drag the divider beside run settings to change its width. Drag the divider above the Run console to adjust its height. When inspecting a response, the divider between request and response adjusts their relative widths.

Dividers can also receive keyboard focus: use arrow keys to resize, Shift for larger steps, and Home/End for the minimum/maximum. Double-click a divider to reset it, or use Reset pane sizes above the workspace. Width limits keep controls usable. On small screens the panes stack and desktop dividers are hidden.

Only numerical pane dimensions are saved in this browser. Payloads, tokens, setup contents, and test modes are not stored as layout preferences. The layout reset does not change your API configuration.

Enable or Disable an Interface

The person starting the local runner can enable both pages for comparison or disable either one afterward. This is a startup setting, not a test scenario setting. Ask the developer or operator to use -ui both, -ui classic, or -ui balanced. A disabled page is unavailable; the test APIs and workload format remain the same.

First Run

Only test APIs you are authorized to use. Start with low traffic against a test or staging system. A run can create or change real records; Load Lab does not remove them afterward.

  1. Select a traffic profile and a short duration, such as 10s.
  2. Enter the API method and full target URL.
  3. Upload a JSON request payload, or edit the request body.
  4. If testing several APIs, use Add scenario. Set percentages totaling 100% for Normal, Burst, or Weighted, or select Multi-API Burst to send every API together.
  5. Add any required headers or bearer token. Set field rules if values should change between requests.
  6. Use the refresh button in Payload preview. Check the generated data.
  7. Confirm authorization, select Start test, and review Run results.

Traffic Profiles

Profile When to use it
Normal Steady traffic. Starts with one user per burst.
Burst Several users arriving together. Starts with 100 users per burst; adjust this before running.
Weighted A custom mix of APIs, such as 30% create, 30% update, and 40% search. Add your own scenarios and percentages.
Multi-API Burst Release every API together in one immediate group, or repeat complete groups at a chosen interval. Percentages do not apply.
Coordinated Every API runs for every virtual user, with the selected shared record. Percentages do not apply.

Normal, Burst, and Weighted select APIs using their configured percentages. Coordinated sends APIs together; it does not wait for one response before calling another or pass IDs between API calls.

Multi-API Burst

Use this profile to test several APIs at the same time, for example to investigate competing updates, locking, or contention.

  1. Select Multi-API Burst and add each API with its own URL, payload, headers, and expected responses.
  2. Set Users / burst. Three APIs with 100 users produces 300 requests per burst: 100 requests to each API.
  3. Choose Single burst to send one group immediately, or Repeated bursts with a repeat interval and duration.
  4. Set Max in flight to at least the displayed request count. Match burst sets this for you.
  5. Generate samples, confirm authorization, and start.

Percentages do not apply. The runner prepares all request bodies before opening one shared start gate. If any body cannot be prepared, that group is not sent. Preparation time is not included in the requested repeat interval; the next interval starts after release. If earlier requests leave too few free slots, an entire repeat group is skipped and counted as dropped arrivals.

All requests are released together, but network and server scheduling can produce small arrival-time differences. Timeouts or slow responses may suggest locking problems; confirm actual deadlocks using server or database logs. This is not a sequence of dependent API calls.

Repeated Runs & Unique Values

Fresh generated values runs your generation rules. Mark an identifier rule Unique when that field must not reuse values from earlier runs on this machine. Only marked fields are protected; ordinary names and unmarked values may repeat.

The local runner keeps a persistent history of reserved values. It retries regex generation when a value has already been used. For flexible string identifiers, an Expression such as "record-" + run_id + "-" + string(sequence) provides a run-specific ID. run_id changes for every actual run; sequence starts at 1 for that run. Use a regex instead when the API requires a strict format or length.

If no unused value is found within 128 attempts, generation fails rather than silently sending a duplicate. Expand the allowed pattern or use a run-specific expression. A small format such as [0-9] only has ten values, so it cannot support unlimited fresh runs. Preview uses a separate temporary history and does not reserve live values.

For contention tests, select Reuse existing / shared records, upload a shared dataset, select One fixed record, and enable overlay on each API. Rules marked Unique are skipped, preserving their literal or dataset IDs; other rules still run. The same record can then be targeted intentionally by every user. A Unique rule is shown as Reused in this mode.

The history is local, not a check against your API database or other machines. Keep the same history between runs and back it up. Clearing it or moving to a new machine removes that protection. Values reserved during failed or stopped preparation remain reserved, even when not sent.

Generate & Inspect Request Bodies

Choose 1, 3, 5, or 10 Samples in Payload preview, then select refresh. Use View to inspect each sample and the download button to save the generated examples. Samples are not requests sent to your target; random values and run IDs will differ during the actual run.

To inspect exactly what was sent, enable Record sent request bodies before starting. After the run, select Inspect beside a request to see its complete sent JSON and the recorded response. The downloaded report pairs these bodies and includes the run ID. If recording was off, the request body cannot be recovered from the report.

Request-body recording is off by default. It can expose test identities, embedded files, and other sensitive values, and large bodies increase report size. Store reports securely. Response bodies are still limited to 2 KiB in web reports.

Traffic Settings

Setting Meaning
Duration How long to schedule requests. Examples: 30s, 2m, 500ms.
Bursts / second How many groups start each second.
Users / burst How many virtual users start in each group.
Max in flight The maximum simultaneous requests. Arrivals beyond this limit are dropped rather than queued.
Request timeout The maximum wait for each response, for example 10s.

For Normal, Burst, and Weighted: planned requests per second = bursts per second × users per burst. In Coordinated mode, multiply that by the number of APIs too.

Example: 2 bursts per second with 10 users per burst plans 20 requests per second. With 3 coordinated APIs, it plans 60. Actual throughput depends on response speed and the in-flight limit.

APIs & Percentages

Each scenario is one API request. Give it a unique name, select its HTTP method, and enter the full URL. Set the request body, data, and authentication separately for each API.

Choose Add scenario to include another API. Switch between the API tabs to edit them. The trash button removes the selected API.

Choose Your Split

For Normal, Burst, and Weighted, each API needs a whole-number percentage from 1 to 100. All percentages together must equal 100%. Examples: 30 / 30 / 40, 25 / 25 / 25 / 25, or ten APIs at 10% each.

The live total shows the remaining or excess percentage. Start stays disabled until the allocation is valid. These are selection probabilities, so a short run may not produce the exact percentage of requests for each API.

Request Payloads

Select Upload request payload and choose a local JSON object, not an array. You can also edit the request body directly. Uploading a replacement payload clears that API's field rules. 

{
  "patient_id": "",
  "first_name": "Test",
  "quantity": 2,
  "unit_price": 15,
  "amount": 0
}

Leave a field unchanged with Keep value, or use field rules to generate it. Nested object fields and array entries are supported.

Test Datasets

A dataset is a non-empty JSON array of records. Use it when your API needs existing test identities or known values. 

[
  {"patient_id": "TEST-001", "first_name": "Alex"},
  {"patient_id": "TEST-002", "first_name": "Sam"}
]

Upload a Scenario dataset for one API. Enable Overlay dataset values to replace matching payload keys. Extra dataset keys are ignored; nested objects are matched recursively. Field rules run after the overlay and can replace these values again.

Cycle records uses records in order; Random record selects a record randomly.

For Coordinated mode, upload a Shared dataset and enable overlay on each API that should use it. Every API for the same virtual user receives the same selected record. Shared record mode can be fixed (the first record), cycle, or random. Coordinated runs use the shared dataset rather than individual scenario datasets.

Select Clear to remove a dataset. Preview always uses the first record; a run uses your chosen selection mode.

Field Rules

Value source What it does
Keep value Preserves the payload value, or its dataset overlay.
Regex Generates a matching string for each request.
Expression Calculates a value using other fields, including numbers and true/false values.
File (base64) Embeds a locally selected file into a string field.

Rules run in displayed order, after dataset overlay. Use the up/down arrows to put a rule before any rule that depends on it. Refer to other fields using body.field_name, or body["key.with.dots"] for a key containing dots.

Examples

Source Pattern or expression
Regex: patient ID PT-[0-9]{8}
Regex: name [A-Z][a-z]{5,9}
Expression: total body.quantity * body.unit_price
Expression: email lower(body.first_name) + "@example.test"
Expression: eligibility body.age >= 18
Expression: synthetic identifier ssn(body.dob, body.gender)

Regex always produces strings, not numbers, and does not guarantee unique values. Use an Expression when you need a numeric or boolean result. Common regex features such as character classes, groups, alternatives, and repeats work; lookarounds, backreferences, and word-boundary assertions do not. Expressions are calculations, not free-text instructions or JavaScript.

The synthetic identifier helper expects a birth date such as 1995-04-15 and a supported gender value such as female or male. It produces test data, not a validated real-world identity number.

Files & Existing Placeholders

For a string field, select File (base64) and choose a local file, such as a PDF. An existing {{file_base64:...}} marker is replaced while keeping its surrounding data-URL prefix. Otherwise, the field receives the file's raw base64 text.

Existing placeholders such as {{uuid}}, {{timestamp}}, {{sequence}}, and {{random_int:8}} are also resolved. They run after field rules, so an expression should refer to literal values or earlier rules rather than an unresolved placeholder.

Headers & Tokens

Open Headers & response settings for the selected API. Enter headers as a JSON object with string values. 

{
  "Content-Type": "application/json",
  "X-Test-Client": "load-lab"
}

If the API needs bearer authentication, enter the token in Bearer token. It updates the Authorization header. Each API can have its own credentials.

Enter Expected status codes separated by commas, such as 200, 201. Other responses count as failures. Leaving this blank accepts any 2xx response.

Use test credentials. Credential headers are excluded from setup exports by default. Enable Include credentials in setup export only when needed, and keep that file private. Request payload data is still included.

Payload Preview

Select the refresh button in Payload preview to generate a sample. It uses the same generation rules as a run without sending a request to the target API. Enter valid API settings and percentages first.

Check types, formats, dependent values, and embedded files. The copy button copies the displayed JSON. Generate another preview after changing the setup. Random values in the actual run will differ.

Start & Stop

If monitoring loses its connection, the status shows DISCONNECTED and retries automatically. Use the reconnect icon to retry immediately. Stop remains available for an active run; monitoring failure does not alter its configured workload.

Confirm that you are authorized to test the targets, then select Start test. Only one run can be active at a time.

Stop prevents new requests from being scheduled. Requests already in flight finish or time out, so the state may show STOPPING briefly. Results are available when the run finishes or stops.

Changing the form does not change a run already in progress. Your current browser setup is not automatically saved; export it before closing or refreshing the page.

Open a Larger Analysis View

Select the external-link icon beside Payload preview, Field rules, or Run results to open a separate tab. Your current form and selected testing mode stay unchanged.

These are read-only snapshots, not live views or extra tests. Preview offers API and sample selection; rules show the configured order, patterns, expressions, and Unique flags; results show per-API summaries and the latest 100 recorded requests with paired bodies.

Use the copy or download icons for the selected JSON or snapshot. The full report remains available in the main workspace. To see later edits or a later run, open a fresh snapshot. If a snapshot expires or is refreshed after its workspace connection closes, reopen it from the workspace.

Snapshots are transferred between local same-origin tabs in memory, without putting request bodies or tokens in the URL or browser local storage. Downloaded snapshots can contain sensitive request or response data.

Interface options contains three static mockups for review. They do not execute requests or replace the current interface.

Run Results

Result Meaning
Completed Requests that finished, including failed responses and network errors.
Failed Network errors and responses outside the expected status codes.
Dropped arrivals Planned requests not sent because the in-flight limit was reached.
Elapsed Time spent scheduling and waiting for active requests to finish.
p95 / p99 95% / 99% of recorded requests finished within this response time.
Body errors Requests that could not be generated from the payload and rules.

The request table shows the latest 100 responses. Select Download report for all recorded responses and the summary. Web reports retain up to 2 KiB of each response body.

Saved Setups

The export button beside Start saves APIs, payloads, datasets, headers, and field rules in one JSON file. Use Import setup to restore that file later.

Import setup accepts a Load Lab export, not a standalone request body or developer configuration. Use Upload request payload for a request-body file instead. Exports contain test data; store them securely. Authorization, token, cookie, secret, and API-key headers are excluded unless you enable credential export.

Imports are checked before replacing your workspace. If a file is invalid, your current setup stays intact. The same setup file can be selected again. A valid replacement payload can also be uploaded when the current request JSON is incomplete.

Identifiers above 9007199254740991 must be JSON strings, not numbers. For example, use "external_id": "9007199254740993". Unsafe numeric integers are rejected rather than rounded. Duplicate or parent/child-overlapping field rules are also rejected.

Common Fixes

Issue What to check
Start is disabled Wait for the current run to finish, or correct the API percentages to total 100%.
Invalid JSON Check commas and double quotes. Payloads must be objects; datasets must be non-empty arrays of objects.
Rule error Check the pattern or expression, field names, value types, and rule order.
Server file reference rejected Select File (base64) for that string field and upload the local file.
401 or 403 responses Check the API's test token, permissions, and required headers.
Network errors or timeouts Check the target URL, API availability, VPN, and request timeout.
Dropped arrivals Lower the request rate or users per burst. Only increase Max in flight if the test system can support it.

Limits & Privacy

The interface is local to this machine. It accepts one active run, a duration up to 1 hour, up to 1,000 in-flight requests, and a request timeout up to 1 minute. Bursts per second may be 1..10,000; users per burst may be 1..100,000. These are tool limits, not recommended starting loads.

Multi-API Burst allows up to 10,000 in-flight requests and 10,000 requests per group. The full group must fit in the configured concurrency. Large payloads and high concurrency can require substantial memory; start small.

JSON uploads are limited to 6 MiB per file, attachments to 4 MiB, and the complete submission to 8 MiB. Embedded file data expands in base64, so a setup with several attachments may exceed the submission limit.

Setup bundles may be up to 16 MiB on disk to accommodate formatted exports, but their compact request submission must still fit within 8 MiB. New exports use compact JSON.

Cycle mode now visits each scenario's dataset in order. Coordinated and Multi-API Burst use the shared dataset only; per-scenario dataset controls are disabled there. Source dataset arrays are copied before generation.

Redirect responses are reported directly rather than automatically changing a POST into a different request. Generation errors produce failed or partial outcomes, and the report separates scheduled, generated, sent, and completed counts. Truncated responses are marked explicitly.

Payloads and credentials are handled by your local runner. They are sent to the targets you configure. Do not use production patient data or other sensitive real-world records for testing. Downloaded reports may contain API response data; treat them as confidential.
